# Real-payment verification before production — 2026-10-05

This is a source review of the current release, not evidence of live PostgreSQL concurrency or payment-provider behaviour. The QA payment provider is mock. `PayMeProvider` still has no checkout, verified webhook or refund implementation. No provider requests, customer reads or database changes were made for this review.

## Current source repairs and QA scope

Claude's final read-only review reported P2, an early return that skipped the per-child payment fence for multi-world packages. That finding describes the source before the final repair. The current `claimChildWorldForCheckout` acquires the child fence and checks other outstanding payment attempts for every child-backed package tier; only continuation-intent registration is restricted to a single complete nine-board world. `startCheckout` now invokes that guard for every tier. A new package containing a world already paid for by that child is also refused before order creation or provider dispatch. Paid historical multi-world games continue to provide their existing worlds, and pending multi-world drafts keep their original payment order rather than receiving a single-world intent.

The focused service verification passed six files and 85 tests, including simultaneous one-world/two-world claims, confirmed unpaid closure, paid-owned overlap for TWO_WORLDS and historical ALL_WORLDS, and pending multi-world draft adoption. TypeScript and `git diff --check` also passed. This fixes P2 in the current source; it does not supply the PostgreSQL concurrency evidence required below. The real-provider exceptions and contracts below are production prerequisites, not defects demonstrated in the mock-payment QA flow.

## Financial lifecycle gaps requiring one consistent implementation batch

1. **Refunding a duplicate charge currently revokes the whole game.** The webhook intentionally preserves two actual paid orders and records `payment:duplicate-order-paid` without generating another game. Both the REFUNDED webhook branch and `refundOrder` nevertheless move the game to REFUNDED when either order is refunded. Multiple generation/recovery services and `guest-sharing.service.ts` also reject any refunded order, even if another order for the game remains paid and unrefunded. Changing only the game's status would therefore give inconsistent access. Implement one payment-entitlement rule across refund, generation and access: refunding only the extra charge preserves a valid paid purchase; refunding the last valid paid purchase revokes access. Do not discard either payment from the financial history.

2. **An admin refund is dispatched before a durable claim.** `refundOrder` calls `c.payment.refund` outside its database transaction, then compare-and-sets the order. Two simultaneous callers can reach the provider before that local claim, and a successful refund followed by a database failure has no durable provider-operation receipt. The real adapter needs confirmed idempotent refund semantics and a durable operation identity/claim/reconciliation flow before automatic retry is enabled. A database-only status change cannot prove the provider was called once.

3. **Historical null checkout fields are not provider evidence.** Older ordinary checkout created its order before the provider call without `checkoutClaimUntil`. A legacy PENDING/FAILED order with no saved checkout URL or provider identifier can represent an undispatched draft or a provider response that was lost. The current mock has a deterministic order session; the real-provider rollout must inspect/reconcile or quarantine ambiguous historical attempts before replacing them. A FAILED notification, a local game deletion or elapsed time alone does not prove a hosted session is closed or cannot charge.

4. **Genuine payment after a supposedly terminal close needs financial reconciliation.** A verified real-provider PAID event must retain the actual money even if an earlier `closed_unpaid` receipt exists. In the current source, the normal confirmed-close path returns an editable game to PACKAGE_SELECTED. A later genuine PAID order cannot transition that game to PAID, so `moveGame` records `payment:game-unreachable` and no generation is queued. The ordinary draft-edit and checkout guards do not treat that paid financial exception as an outstanding checkout; a parent could change the draft and open another payment. A second genuine payment is recorded as a duplicate, but does not repair the unreachable game, and a remaining open payment cannot be closed through the unpaid-only closure flow. Before real payments, atomically preserve the payment, record a distinct reconciliation incident, freeze further draft mutation and checkout, and provide an operational financial settlement path. Do not blindly generate from the now-mutable draft: its photo, age or world selection may have changed after closure. Settle the verified payment against an immutable original purchase or refund it under the durable refund rule above; do not count an unresolved incident as a completed sale. This is a provider-contract breach/reconciliation scenario for a real adapter. The mock rejects payment after its durable terminal-close receipt, so this does not describe a reachable mock QA failure.

## Real-provider contracts and bounded operation time

Implement and verify the actual PayMe merchant contract before enabling the adapter. Accepting an idempotency field is not evidence of provider support. Repeating checkout with the same immutable order key and request must return the same payment attempt, including after an accepted request whose acknowledgement was lost. The provider must not recreate a payable session from that key after a successful terminal close. Verify signed webhook event identity, amount, currency, replay handling and authoritative status reconciliation independently of the browser return URL.

`closeCheckout` may return `closed_unpaid` only when the provider establishes that the complete attempt was never paid and cannot subsequently accept or capture payment. This guarantee must cover an in-flight checkout creation and later retries using the same attempt key. `paid`, timeout, transport failure, ambiguous status and unsupported closure do not authorize clearing the order key or unlocking another checkout. Preserve and reconcile genuine payment that contradicts an earlier close receipt through the financial-exception path above.

The current checkout and closure claim leases last 120 seconds. Real adapter operations need explicit deadlines shorter than their respective lease, with margin to persist the result; this includes checkout creation and terminal closure, plus an independently bounded refund/reconciliation operation. A local timeout or abort stops waiting and records an unknown outcome; it cannot prove the provider stopped processing. Never release an unknown payment attempt, invent a new operation key or unlock another child checkout because the deadline or lease elapsed. Retry/reconcile the same immutable attempt only under the provider's verified idempotency contract.

## Missing PostgreSQL service-concurrency evidence

SQLite tests prove the asserted outcomes on SQLite; its single-writer behaviour does not establish PostgreSQL Serializable conflict handling. Before real-payment production, use a disposable isolated PostgreSQL schema with two independent Prisma clients and synthetic fixtures only. Apply the complete service schema to that namespace, verify its columns/constraints/indexes, and ensure all model and raw-query access resolves to that namespace. Never run this harness against customer schemas. Use local fake payment/storage adapters, synthetic parent/child identifiers, authored public board metadata and generated one-pixel assets; no uploaded photos, generation calls, emails or real payment requests.

Force requests to overlap before their row fences, without waiting at a barrier while holding a row needed by the other request. Record which transaction overlaps and any P2034 retry. Required cases:

- Concurrent same-world starts produce one `ChildWorldPurchase` and one active unpaid game, and retries return that same game.
- Concurrent child-backed checkout claims across different worlds and ordinary 18-board packages produce at most one outstanding payable attempt. Re-entering a claimed checkout preserves its exact order and provider key.
- A payment for world A racing checkout for world B either blocks B until retry or prices B from the committed same-child paid history. It must not dispatch an obsolete first-purchase price.
- Simultaneous deliveries with the same webhook event ID produce one event and one status transition. Different PAID event IDs for the same order produce one completed-purchase analytics event. Distinct paid orders preserve both amounts and audit the extra payment without another generation.
- Payment racing confirmed closure in both orders preserves money if payment wins, or rejects later mock payment if the durable terminal-close receipt wins. Unknown closure and expired dispatch leases remain outstanding; neither unlocks a new session.
- With the real-provider exception batch implemented, simulate a genuine signed PAID after confirmed close while the game is PACKAGE_SELECTED and after a draft edit. Preserve the actual payment, freeze mutation and repeat checkout, emit one reconciliation incident, and do not enqueue the changed draft or report a resolved sale. Verify the chosen financial settlement path and any remaining open sibling attempt.
- With the consistent refund batch implemented, refund only the duplicate order and verify generation, owner play and friend access remain valid; refund the remaining paid order and verify access is revoked. Exercise webhook/admin paths and simultaneous refunds of distinct orders. Verify the provider-operation receipt for accepted-but-acknowledgement-lost refunds.
- Concurrent guest snapshot deltas merge into a union without lost finds or duplicated revisions. Repeated joins with the same join key produce one participant.
- Guest writes racing revoke, remove or fenced game deletion cannot recreate deleted results or credentials. Delayed storage reads recheck revocation before returning media. Cascades remove both share and participant rows.
- Marking an observed report revision seen while a new find arrives does not mark the later update seen.

Verify invariants after the contenders finish, repeat failed Serializable requests through the supported service retry path, and remove only the verified synthetic schema after the run. PostgreSQL evidence supplements the source/SQLite/browser checks; real-provider terminal-close, checkout-idempotency and refund contracts still require separate verified adapter evidence.
